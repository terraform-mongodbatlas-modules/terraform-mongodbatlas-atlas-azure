# Upgrade Guide: v0.2.x to v0.3.0

This guide covers breaking changes when upgrading to v0.3.0 of the MongoDB Atlas Azure module. The module remains in public preview; treat upgrades as you would any pre-v1 module.

- [BYOE variable rename (AWS-aligned names)](#byoe-variable-rename-aws-aligned-names)
- [Configurable Timeouts](#configurable-timeouts)
- [Region key normalization](#region-key-normalization)
- [Private Endpoint Regional Mode (Breaking Change)](#private-endpoint-regional-mode-breaking-change)
- [Backup export: module-managed storage](#backup-export-module-managed-storage)

## BYOE variable rename (AWS-aligned names)

The BYOE (bring-your-own-endpoint) PrivateLink variable names were aligned with the [Atlas AWS module](https://registry.terraform.io/modules/terraform-mongodbatlas-modules/atlas-aws/mongodbatlas/latest) so the same names work across cloud providers, **future proof** the module as APIs and shared patterns evolve, and **match the underlying resources**—the Atlas PrivateLink endpoint (`privatelink_byo_endpoint`) and the user-managed private endpoint you register with Atlas (`privatelink_byo_service`).

| Previous name | New name |
| --- | --- |
| `privatelink_byoe_regions` | `privatelink_byo_endpoint` |
| `privatelink_byoe` | `privatelink_byo_service` |

### Who is affected?

Users of the BYOE PrivateLink pattern who still use the old variable names.

### Required action

Rename the variables. Each entry in `privatelink_byo_endpoint` is an object with a `region` field (Atlas or Azure format). User-defined **map keys** (for example `primary`, `pe1`) are unchanged, so you typically do **not** add `moved` blocks for the rename—resource addresses that use those keys stay the same.

**Before (old names):**

```hcl
module "atlas_azure" {
  source  = "terraform-mongodbatlas-modules/atlas-azure/mongodbatlas"
  # version: use the last release that still documented privatelink_byoe_*

  project_id = var.project_id

  privatelink_byoe_regions = {
    primary = "eastus2"
  }

  privatelink_byoe = {
    primary = {
      azure_private_endpoint_id         = azurerm_private_endpoint.atlas.id
      azure_private_endpoint_ip_address = "10.0.2.100"
    }
  }
}
```

**After (new names):**

```hcl
module "atlas_azure" {
  source  = "terraform-mongodbatlas-modules/atlas-azure/mongodbatlas"
  # version: bump to a release that exposes privatelink_byo_*

  project_id = var.project_id

  privatelink_byo_endpoint = {
    primary = { region = "eastus2" }
  }

  privatelink_byo_service = {
    primary = {
      azure_private_endpoint_id         = azurerm_private_endpoint.atlas.id
      azure_private_endpoint_ip_address = "10.0.2.100"
    }
  }
}
```

After the rename, you can still use either workflow for BYOE: One `terraform apply` that creates both Atlas private link services and registered user endpoints, or an initial apply for `privatelink_byo_endpoint` (and outputs such as `privatelink_service_info`) followed by a second apply after your Azure private endpoints exist. The module does not use numbered phases, pick the order that matches how you manage Azure networking.

## Configurable Timeouts

v0.3.0 introduces a `timeouts` variable with `create`, `update`, and `delete` fields defaulting to `"30m"`. The module applies these timeouts to each wrapped resource where the Terraform provider exposes a `timeouts` block or, for `mongodbatlas_encryption_at_rest_private_endpoint`, a `timeouts` attribute on the resource.

### Who is affected?

**Existing deployments upgrading from v0.2.x** that use the default `timeouts` configuration (unset, `timeouts = {}`, or a partial object that still applies module defaults) will see a plan diff on the **first** `terraform plan` (or `apply` plan) **after** you bump the module to v0.3.0. The diff is the new `"30m"` module-managed timeout settings where the previous module version did not set timeouts. The change is an in-place update, not a forced replacement: Terraform updates timeout metadata in state; it does not destroy infrastructure solely because of this diff. If you set `timeouts = null` before that first plan, the module does not add those blocks, so you avoid the diff; see [Zero-diff upgrade](#zero-diff-upgrade) below.

### Why the change?

PrivateLink and encryption private endpoint operations can fail or stall. The default long waits in the provider are often longer than teams want. A single `timeouts` object with practical defaults (and the option to keep provider defaults) gives predictable behavior without per-resource variables.

### Zero-diff upgrade

Set `timeouts = null` to skip all module-managed timeout blocks and attributes and keep each provider’s own defaults.

```terraform
module "atlas_azure" {
  source  = "terraform-mongodbatlas-modules/atlas-azure/mongodbatlas"
  version = "~> 0.3"
  # ...
  timeouts = null
}
```

After you upgrade the module source to v0.3.0:

1. Run `terraform plan` with `timeouts = null`. The plan should not add or change module-managed `timeouts` blocks.
2. Run `terraform apply` if you are ready to align state with that configuration.

When you want the 30m defaults (or custom values), remove `timeouts = null` or set `timeouts = {}` for the default 30m create, update, and delete values. You can also set a partial object; omitted keys use the 30m default for those operations.

```terraform
module "atlas_azure" {
  # ...
  timeouts = {
    create = "45m"
    # update and delete default to 30m
  }
}
```

## Region key normalization

`for_each` keys and several output maps that are keyed by region now use **normalized Azure location** strings (for example `eastus2`) instead of raw input strings when those differ (for example Atlas format `US_EAST_2`).

Affected areas include:

- `module.privatelink[...]`
- `module.encryption_private_endpoint[...]` (when used)
- Output maps such as `privatelink`, `privatelink_service_info`, and `encryption.private_endpoints`

### Who is affected?

Only users who passed **Atlas-format** region strings to inputs that drive those keys, such as:

- `privatelink_endpoints[].region`
- `privatelink_byo_endpoint.*.region`
- `encryption.private_endpoint_regions`

If you already use **Azure location** format (`eastus2`) everywhere, you typically do not need to migrate state for key normalization.

### How to check

After upgrading the module, run `terraform plan`. If you see destroy/create pairs driven by address changes, for example:

```text
# module.atlas_azure.mongodbatlas_privatelink_endpoint.this["US_EAST_2"] will be destroyed
# module.atlas_azure.mongodbatlas_privatelink_endpoint.this["eastus2"] will be created
```

you need root-module `moved` blocks or `terraform state mv` (see below).

### Migration with `moved` blocks (recommended)

Add `moved` blocks in your **root** module for each affected Atlas-format key. Replace `module.atlas_azure` with your actual module instance name.
See the variable description [atlas_to_azure_region](../README.md#atlas_to_azure_region) for all the possible mappings.

**PrivateLink (module-managed)** — two `moved` blocks per region:

```hcl
moved {
  from = module.atlas_azure.mongodbatlas_privatelink_endpoint.this["US_EAST_2"]
  to   = module.atlas_azure.mongodbatlas_privatelink_endpoint.this["eastus2"]
}

moved {
  from = module.atlas_azure.module.privatelink["US_EAST_2"]
  to   = module.atlas_azure.module.privatelink["eastus2"]
}
```

**Encryption private endpoints** — one `moved` block per region:

```hcl
moved {
  from = module.atlas_azure.module.encryption_private_endpoint["US_EAST_2"]
  to   = module.atlas_azure.module.encryption_private_endpoint["eastus2"]
}
```

After a clean plan and successful apply, remove the temporary `moved` blocks.

### Migration with `terraform state mv` (alternative)

```bash
terraform state mv \
  'module.atlas_azure.mongodbatlas_privatelink_endpoint.this["US_EAST_2"]' \
  'module.atlas_azure.mongodbatlas_privatelink_endpoint.this["eastus2"]'

terraform state mv \
  'module.atlas_azure.module.privatelink["US_EAST_2"]' \
  'module.atlas_azure.module.privatelink["eastus2"]'

terraform state mv \
  'module.atlas_azure.module.encryption_private_endpoint["US_EAST_2"]' \
  'module.atlas_azure.module.encryption_private_endpoint["eastus2"]'
```

### Output key changes

Update references that index outputs by the old key format, for example:

- `module.atlas_azure.privatelink["US_EAST_2"]` → `module.atlas_azure.privatelink["eastus2"]`
- `module.atlas_azure.privatelink_service_info["US_EAST_2"]` → `module.atlas_azure.privatelink_service_info["eastus2"]`
- `module.atlas_azure.encryption.private_endpoints["US_EAST_2"]` → `module.atlas_azure.encryption.private_endpoints["eastus2"]`

A short Atlas-to-Azure reference:

| Atlas format | Azure format |
| --- | --- |
| US_EAST_2 | eastus2 |
| US_WEST_2 | westus2 |
| EUROPE_WEST | westeurope |

The module ships a full mapping in `variables_generated.tf` (`atlas_to_azure_region`).

## Private Endpoint Regional Mode (Breaking Change)

v0.3.0 adds a `privatelink_regional_mode` variable (`"auto"` or `"disabled"`, default `"disabled"`). The module creates `mongodbatlas_private_endpoint_regional_mode` only when the value is `"auto"` and the configuration has multiple distinct Atlas service regions (see [regionalized private endpoints for multi-region sharded clusters](https://www.mongodb.com/docs/atlas/security-private-endpoint/?cloud-provider=azure#-optional--regionalized-private-endpoints-for-multi-region-sharded-clusters)).

In v0.2.x, the module turned on private endpoint regional mode automatically whenever it detected more than one Atlas region.

### Why the change?

Some deployments need multiple regions or multiple PrivateLink endpoints without per-region SRV records or connection strings. Because project-wide regional mode also has operational impact, the module now uses an opt-in default.

### Who is affected?

- Users with **more than one distinct Atlas service region** in `privatelink_endpoints` or `privatelink_byo_endpoint` who **relied on automatic regional mode** in v0.2.x.
- Anyone who reads `regional_mode_enabled` and assumed it was `true` whenever multiple service regions were present (it is now `true` only when `privatelink_regional_mode = "auto"` and multiple regions exist).

**No action** if you use a single Atlas region for PrivateLink.

### Required action

To keep the same behavior as v0.2.x (create `mongodbatlas_private_endpoint_regional_mode` when the module would have done so before), set:

```terraform
privatelink_regional_mode = "auto"
```

Add this to your `module` block next to your other `privatelink_*` settings.

### Plan after upgrade

If you **do not** set `privatelink_regional_mode = "auto"` and you previously had multiple Atlas service regions, `terraform plan` may show that `mongodbatlas_private_endpoint_regional_mode` will be **destroyed**. That is expected: the resource is no longer created unless you opt in. Confirm that your applications and connection strings do not require per-region SRV before you apply. If they do, set `privatelink_regional_mode = "auto"` before applying.

## Backup export: module-managed storage

For module-managed `backup_export` storage, the module sets `public_network_access_enabled` to `true` on the Storage Account so MongoDB Atlas can reach the blob endpoint for export. Optional `azurerm_storage_management_policy` for export-blob retention defaults `expiration_days` to **365** (AWS parity), **0** disables the policy.

### Public network access

**Who is affected?** Users who use `backup_export` with `create_storage_account.enabled = true` should expect the account to allow the public network path the Azure provider uses for that flag. MongoDB Atlas needs a reachable storage endpoint for this integration; turning public network access off on the account breaks export.

### Why the change?

Module-managed storage aligns with `log_integration` module-managed storage: both keep `public_network_access_enabled` enabled for Atlas connectivity while using a private container, blocking nested public blob access, and enforcing minimum TLS 1.2.

### Required action (public network)

- If you must use a storage account with public network access disabled, provide your own account with `storage_account_id` and configure networking (for example private endpoints) so Atlas and your operations can still reach blob storage in line with your standards.
- If a prior plan or doc assumed `public_network_access_enabled` was `false` on module-managed accounts, expect a plan change to `true` when you align with the current module.

### Storage management policy (expiration)

`expiration_days` is a new field on `create_storage_account` (default: **365** for backup export). A new `azurerm_storage_management_policy` resource appears in the plan when the value is greater than zero.

**Who is affected?** Users with **module-managed** `backup_export` storage. The plan shows a new `azurerm_storage_management_policy` (rule name `atlas-backup-export-expiration`).

### Required action (lifecycle)

No action required if the lifecycle rules are acceptable. To opt out, set `expiration_days = 0`:

```terraform
backup_export = {
  enabled = true
  # ...
  create_storage_account = {
    enabled         = true
    # ...
    expiration_days = 0
  }
}
```

### Zero-diff option

Set `expiration_days = 0` before upgrading. No management policy resource for backup export appears in the plan. There is no in-module zero-diff for only `public_network_access_enabled`; the module enforces `public_network_access_enabled = true` on module-managed accounts in v0.3.0+ so Atlas can use the integration.
